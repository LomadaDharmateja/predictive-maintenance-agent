## 1. Source

**Microsoft Azure Predictive Maintenance dataset**
<https://www.kaggle.com/datasets/arnabbiswas1/microsoft-azure-predictive-maintenance>

The data is **simulated**, not collected from a physical plant. It was created by
Microsoft as a teaching dataset for the Predictive Maintenance Modelling Guide. No
claim in this repository about real-world performance, downtime, or cost is
supportable from it, and none is made.

A synthetic parts inventory is generated by `scripts/generate_inventory.py` (seeded).
It is not part of the source dataset. See section 6.

### Getting the files

Four of the five source files are committed under `data/raw/` (260 KB in total).
`PdM_telemetry.csv` is not: at 77 MB it would roughly triple the repository, and
history is not something you can trim back afterwards without a rewrite. Download it
from the Kaggle link above and place it at `data/raw/PdM_telemetry.csv` before running
`make data`:

```
size    80,142,329 bytes
sha256  d957f3c45bb83416b716600da8cffd72f4b6961db89867d9696ad19f7cb1bd4e
```

Until it is present, `make data` aborts with a message naming the missing path, and
`pytest` skips the whole suite with the same explanation rather than reporting green
against absent data.

## 2. Tables

| Table | Rows | Columns | Nulls |
|---|---|---|---|
| `telemetry` | 876,100 | datetime, machineID, volt, rotate, pressure, vibration | none |
| `errors` | 3,919 | datetime, machineID, errorID | none |
| `maint` | 3,286 | datetime, machineID, comp | none |
| `failures` | 761 | datetime, machineID, failure | none |
| `machines` | 100 | machineID, model, age | none |

The `failure` column in the `failures` table holds a component identifier
(`comp1`-`comp4`), not a boolean. It keeps its source name so the raw file and the
database table agree, but it reads as a trap and is called out here for that reason.

### Key integrity

`machineID` is the primary key of `machines` (100 unique values) and a foreign key in
every other table. **Zero orphan IDs** in telemetry, errors, maint or failures.

`failures` covers 98 of 100 machines — two machines never failed in the observation
window. This matters for machine-holdout splits: a small holdout may contain very few
or no failure events.

### Domain values

- Components: `comp1`, `comp2`, `comp3`, `comp4`
- Error types: `error1`, `error2`, `error3`, `error4`, `error5`
- Machine models: `model1`, `model2`, `model3`, `model4`
- Machine age: 0 to 20 (years)

## 3. Time coverage

| Table | From | To |
|---|---|---|
| telemetry | 2015-01-01 06:00 | 2016-01-01 06:00 |
| errors | 2015-01-01 06:00 | 2016-01-01 05:00 |
| maint | **2014-06-01 06:00** | 2016-01-01 06:00 |
| failures | 2015-01-02 03:00 | 2015-12-31 06:00 |

Telemetry is a **balanced hourly panel**: 8,761 distinct timestamps x 100 machines =
876,100 rows. Every machine has exactly 8,761 readings. No gaps, no duplicates.

Two consequences to handle explicitly:

1. **`maint` begins seven months before telemetry.** This is intentional in the source
   data. It means replacement history is available for every machine from the first
   telemetry hour, so time-since-last-replacement features are computable at t=0
   without reaching into the future.
2. **Telemetry extends past the last failure.** Failures end 2015-12-31 06:00 while
   telemetry and errors run to 2016-01-01 06:00 and 2016-01-01 05:00 respectively.
   The final 24 hours of telemetry have an incomplete label window: a row there
   cannot be confirmed negative, only unobserved. These rows are trimmed from the
   modelling set, and the trim boundary is asserted in a test rather than assumed.

## 4. Target

761 failure events over 876,100 telemetry hours = **0.0869%**.

A model that always predicts "no failure" achieves **99.9131% accuracy**. Accuracy is
therefore not reported anywhere in this project. Evaluation uses precision, recall,
PR-AUC, and the confusion matrix, against a majority-class baseline.

By component:

| Component | Failure events |
|---|---|
| comp2 | 259 |
| comp1 | 192 |
| comp4 | 179 |
| comp3 | 131 |

### Label definition

A telemetry row at time `t` for machine `m` is labelled positive for component `k` if
a failure of `k` on `m` occurs in the interval `(t, t + 24h]`.

This is modelled as **four independent binary problems**, one per component, rather
than a single multiclass problem — the downstream agent needs a per-component
probability in order to decide which part to reserve.

Approximate positive rates under this labelling: ~2.1% overall; comp2 ~0.71%,
comp1 ~0.53%, comp4 ~0.49%, comp3 ~0.36%. Still severely imbalanced.

Cost assumption. A missed failure is treated as 10x the cost of a false alarm: a missed failure means unplanned downtime and an emergency part order, while a false alarm costs one unnecessary part and one technician visit. This ratio is an assumption, not a measurement, and it is the basis for threshold selection in place of an arbitrary 0.5 cutoff.

## 5. Known leakage risks

### 5.1 `maint` contains the answer

**743 of 761 failure records (97.6%) also appear in `maint`** as a
`(machineID, datetime, component)` match.

This is causally correct: a failure triggers an unscheduled component replacement,
logged at the same timestamp. It is not a data error. It is a leakage trap.

**Rule:** any feature derived from `maint` at prediction time `t` must be computed
only from records with `datetime < t`. Strictly less than, never `<=`. A
"days since last replacement" feature built without this constraint collapses to zero
at the exact moment of failure and hands the model the label.

This constraint is to be enforced by test, not by convention.
`tests/test_no_future_leakage.py` does not exist yet — it belongs with the feature
layer, which has not been built. Until it does, this rule is convention.

#### The 18 failure records with no `maint` match

Investigated by `scripts/investigate_failure_maint_gap.py`, which is committed and
reproduces every figure below. Run it with `make investigate`.

**The +/- 1 hour hypothesis is refuted.** Widening the match window recovers nothing
at any plausible tolerance:

| Window | Matched | Unmatched |
|---|---|---|
| exact | 743 | 18 |
| +/- 1h | 743 | 18 |
| +/- 3h | 743 | 18 |
| +/- 12h | 743 | 18 |
| +/- 24h | 745 | 16 |
| +/- 7d | 751 | 10 |
| +/- 30d | 757 | 4 |

**What the 18 records actually are.** They are exactly, and only, the failure rows
timestamped `2015-01-02 03:00:00` — one batch, one timestamp, 18 rows across 17
machines (machine 16 appears twice, for `comp1` and `comp3`).

Two facts make the batch anomalous:

1. All 3,286 `maint` records are stamped at 06:00. So are the other 743 failure
   records. These 18 rows are the only off-grid timestamps in either table.
2. No `maint` record exists anywhere in the dataset at `2015-01-02 03:00:00`.

**Timestamp rounding is ruled out, not confirmed.** In both `failures` and `maint`
the minute and second fields take exactly one value: zero. There is no sub-hour
precision for a +/- 1 hour window to recover, and a 3-hour offset is not a rounding
artifact.

**The nearest replacement is days away, not hours.** For each of the 18, the closest
`maint` record for the same `(machineID, component)` pair sits between 21 hours and 65
days from the failure; the median nearest record *precedes* the failure by 4 days
21 hours. Every affected pair does appear in `maint` elsewhere (5 to 11 times each),
so this is not a component type missing from the log.

**What this means.** These 18 failures have no corresponding replacement event at all.
The mechanism is established; the upstream cause is not. The batch sits 21 hours after
the first telemetry reading (`2015-01-01 06:00`), and for 17 of the 98 machines that
ever fail it is their first failure, which is consistent with an initialisation
artifact in the source simulator — an initial failed-component state emitted as a
failure event without a paired maintenance event. `UNVERIFIED:` no generator,
changelog, or provenance note for the Microsoft source data is available in this
repository, so that reading is a hypothesis and is not treated as fact anywhere
downstream.

**Handling.** The records are retained. They are valid failure events under the label
definition in section 4. Because they all fall inside the first 21 hours, any warm-up
trim applied to the modelling set will remove all 18 at once; if that happens it must
be a stated decision, not a side effect.

### 5.2 Temporal autocorrelation

Adjacent hourly readings for the same machine are near-identical. A random row split
places near-duplicate rows on both sides of the boundary and inflates every metric.

**Rule:** splits are temporal. Random row splits are not used anywhere in this
project.

| Split | Period |
|---|---|
| Train | 2015-01 to 2015-09 |
| Validation | 2015-10 |
| Test | 2015-11 to 2015-12 |

Cross-validation within train uses rolling origin, not k-fold.

**Consequence, stated honestly:** the test period contains roughly 127 failure events.
Recall estimated on this set carries substantial uncertainty and is reported with a
confidence interval, not as a point estimate.

A secondary evaluation holds out machines rather than time, to measure generalisation
to unseen units. Given that two machines never fail, holdout composition is checked
for failure coverage before use.

## 6. Synthetic parts inventory

Generated by `scripts/generate_inventory.py` with seed `20240601`. Not source data.

Keyed on values that actually exist in the dataset — `comp1`-`comp4` and
`model1`-`model4`. The generator reads those values out of `PdM_maint.csv` and
`PdM_machines.csv` rather than hardcoding them, so the inventory cannot drift away
from the fleet it describes.

Fields: `part_id`, `component`, `compatible_models` (pipe-separated), `stock_quantity`,
`unit_cost`, `supplier_id`, `lead_time_days`.

**9 parts** (comp1: 2, comp2: 1, comp3: 3, comp4: 3), drawn from a pool of 5
suppliers of which 4 are used at this seed. For each component the four machine
models are partitioned
into disjoint groups, one part per group, so every `(component, model)` pair resolves
to exactly one part. The generator asserts this coverage before writing, and
`tests/test_schemas.py` asserts it again against the source files.

Randomness uses `random.Random`, whose Mersenne Twister stream CPython documents as
reproducible across versions. NumPy's `Generator` does not carry the same guarantee
and is deliberately not used.

The generator is committed alongside its output so the inventory is reproducible. Any
result that depends on inventory values is a result about simulated logistics and is
labelled as such. Costs, stock levels, suppliers and lead times are invented; none of
them is a measurement.

## 7. Out of scope

The following were part of an earlier version of this project and have been removed.
They are retained under `archive/v1-data/` for reference only.

| Removed | Reason |
|---|---|
| AI4I 2020 maintenance data | 10,000 rows, 10,000 unique product IDs — no machine entity and no time dimension, so no fleet could exist |
| Supply chain table | `Actual_Demand` contained a single repeated Python lambda repr across all 2,342 rows; no key linking it to any machine |
| World Bank commodity prices | Real data, but macroeconomic and unrelated to any machine in the fleet; category labels are also incorrect in the source file |
| WEG electric motor manual | A genuine vendor manual, but for electric motors, while the machine data described milling equipment — the retrieval layer was ungrounded |

The v1 application layer that consumed this data — the Streamlit UI, the LangChain
agent, the Pinecone retrieval layer, the commodity and supplier tools, the LangGraph
sketch, and the RandomForest pickle trained on the AI4I table — is retained under
`archive/v1-app/` for the same reason. None of it is imported by anything in `src/`.

The AI4I data is kept because it is intended to be the subject of a data-leakage case
study. `docs/LEAKAGE_CASE_STUDY.md` has not been written yet.

## 8. Building the database

```
make data      # generate the inventory, then rebuild data/pdm.db from data/raw/
make test      # pytest
make verify    # profile the raw files without building anything
make investigate  # reproduce the section 5.1 analysis
```

`make data` deletes `data/pdm.db` and rebuilds it. It does not migrate in place.

**Determinism.** Two consecutive clean builds produce a byte-identical file
(`sha256 d91911e9...`, 136,261,632 bytes on SQLite 3.x with `page_size=4096`). The
pipeline reads no clock, no environment variable and no network, and contains no
randomness; the only seeded randomness in the data layer lives in
`scripts/generate_inventory.py`. `tests/test_ingest.py::test_rebuild_is_byte_identical`
asserts this. The byte hash is a property of the SQLite build as well as the data, so
it is recorded here as an observation, not as a cross-platform guarantee — the
per-table content hashes in `data/generated/build_manifest.json` are the portable
check.

**Tables.** One per source file, plus `parts_inventory`. `machineID` is
`INTEGER PRIMARY KEY` on `machines` and a declared `FOREIGN KEY` on all four event
tables, with `PRAGMA foreign_key_check` run before commit. Each event table has a
primary key over its natural key, so a duplicated source row aborts the build rather
than being inserted twice or silently ignored. Indexes exist on `(machineID, datetime)`
for all four event tables, and on `datetime` alone for `telemetry` and `failures` to
support the temporal splits in section 5.2.

Timestamps are stored as `TEXT` in `YYYY-MM-DD HH:MM:SS`, which sorts lexically in
chronological order. `tests/test_ingest.py::test_datetime_is_stored_sortable` asserts
this, because every date range query in the project depends on it.
