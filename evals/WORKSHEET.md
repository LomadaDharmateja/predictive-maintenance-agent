# WORKSHEET.md

Fifteen machine-hours from the validation split, chosen by named
predicate, for writing `evals/scenarios.yaml` against. Generated by
`make worksheet`; every figure is computed, none typed.

Validation window: `2015-10-01 00:00:00` to `2015-10-17 23:00:00` (408 hourly prediction times, 40,800 machine-hours).

Prediction horizon: 14 days. Model family: `logreg`. Probabilities are isotonic-calibrated, computed with the same artefacts `get_failure_risk` loads.

**The test split was not opened.** This script reads `load_val()` only.

---

## 1. Component reference

Constant across every machine and every hour below. The detection lead
is a fleet-level measurement, and the calibration flag is a property of
the model, so neither varies row to row.

|---|---|---|---|---|---|
| comp1 | 24.0 | `false` | +0.0049 | [-0.1041, +0.0251] | insufficient |
| comp2 | 335.0 | `true` | +0.0667 | [+0.0227, +0.0945] | insufficient |
| comp3 | 326.5 | `false` | +0.1540 | [-0.4086, +0.2650] | insufficient |
| comp4 | 335.0 | `false` | +0.1203 | [-0.0318, +0.1983] | marginal |

Component-level `warning_adequacy` is the best verdict any of that
component's parts achieves. Because both inputs -- the measured lead and
the part lead time -- are fleet constants, **`warning_adequacy` does not
vary by machine or by hour**. A scenario contrasting two components'
adequacy is therefore a contrast that holds for every machine; the pick
labelled `adequacy-split` below is the one where both components also
carry enough probability for the contrast to matter.

### On the requested out-of-stock case

**No part in the inventory is out of stock.** The minimum stock level is 4 units (`PN-COMP4-001`, comp4, 12-day lead). A scenario asserting a zero-stock part would assert something the data does not contain, and the agent would contradict it.

The `scarcest-part` pick below substitutes the lowest-stock part
instead. If a genuine out-of-stock scenario is wanted, the inventory
generator (`scripts/generate_inventory.py`) is where a zero would have
to come from -- not from the scenario file.

## 4. The fifteen

Two constraints run across the whole set. **No machine appears twice**,
so fifteen scenarios exercise fifteen machines rather than fifteen hours
of one. **No two picks share a time band** -- the window is cut into
15 equal bands and each pick claims one, so the set spans the
validation period instead of clustering wherever a score peaks.

Both constraints bind on the selectors that run later. A selector
described as picking a maximum picks the maximum among rows still
available to it, which is not always the fleet maximum; where that
distinction matters the entry below says so.

## 5. What this worksheet does not establish

- Every row is simulated data (Microsoft Azure PdM). An outcome column
  reading `yes` means the simulation recorded a failure, not that a
  machine broke.
- The outcome column is the label the model was trained against. A
  scenario must not ask the agent for it: no tool returns it, and an
  answer that supplied it would be a fabrication that happened to match.
- Three of the four components carry `calibrated: false`. Their
  probabilities appear above because the tool returns them, not because
  they are established as meaningful.
- Fifteen rows chosen to be interesting are not a sample. Nothing here
  supports a statement about how the fleet behaves on average.
